## 1. 三条底线

任何改动都不能破坏这三条（都有测试或结构在守）：

1. **不产出可疑固件。** 参数不确定、容量校验不过、架构不匹配 —— 一律拒绝。
   "能编但错"比"编不过"危险得多。
2. **安全接管。** 写工程的东西必须经 `managed.Owned`；非本工具产物先备份。
3. **零第三方运行时依赖 + 结构不变量。** `dependencies = []`、分层、单模块 ≤700 行、
   data/assets 单一入口、命令面冻结 —— 由 `tests/test_architecture.py` 强制。

## 2. 架构与数据流

```text
入口名(.cmd/wrapper) ──> cli.main(argv)
   ├─ 折叠 -Fpu "<dash-value>"        (_fold_dash_value)
   ├─ argparse (add_help=False, allow_abbrev=False)  → verb + 选项
   ├─ project.find_root(当前目录向上 6 层)            → 工程根
   ├─ model.resolve(-Target, root)                    → 后端 (detect_score)
   ├─ discovery.discover()                            → Toolchain (ARM 前缀)
   ├─ backend.extract(root, opt) = build_model()      → ProjectModel
   │     └─ 设备表 → cpu/fpu 或 arch/abi/toolchain；ld/内存校验；拒绝结论
   ├─ 若 model.toolchain 与已发现前缀不同 → discovery.discover(prefix=…) 重查
   └─ backend.<verb>(Context)                         → Result(code)
```

关键设计：

* **`ProjectModel` 是唯一跨后端契约**：芯片、宏、头文件、源集合、`opt/dbg`、拒绝列表、
  以及 `extra` 里的后端私有数据。后端只填它，动作只读它。
* **拒绝优先于一切写入**：`apply_chip_params` / `apply_memory_plan` 在 `build_model` 阶段
  就把"不可做"的理由写进 `model.refusals`；`action_init` 第一件事就是照它返回，
  **不写任何文件**。
* **两层 make 入口**：B 档 `xtcli/Makefile`+`config.mk`+`rules.mk`（工具生成）；
  A 档工程自带 `Makefile`（只调用、不接管）。
* **后端可插拔**：只有 `model.load_backends()` 导入 `xtcli.backends.*`；
  `cli.py` 不认识任何后端。

## 4. 加一颗新芯片 / 新厂商

**只加一个 JSON 文件，不改代码**（这是刻意的设计：命名规则不进代码）。

### 4.1 步骤

1. 新建 `data/devices/<厂商>.json`（`schema_version: 1`），字段见下；
2. 用真实型号试查：

   ```powershell
   .\.venv\Scripts\python.exe -c "import sys;sys.path.insert(0,r'E:\env\xtcli\src');from xtcli import devices;t=devices.load_tables();print(devices.device_info_any('你的型号',t))"
   ```
3. 跑 `python -m unittest discover -s tests -t tests`（`test_devices_breadth.py` 会核对
   "表里写的 openocd cfg 在本机是否存在"、"非 ARM 必须有 arch"、"memory 必须有出处"）；
4. 若是新厂商的**工程形态**，用真实工程跑一次 `xtcli-init-pj` + `xtcli-build-pj`。

### 4.2 表结构

```jsonc
{
  "schema_version": 1,
  "vendor": "GigaDevice",
  "_comment": ["用途", "来源规则", "哪些没写、为什么"],
  "families": {
    "GD32F103": {                       // 键 = 型号前缀（最长匹配，大小写不敏感）
      "cpu": "cortex-m3",               // GCC -mcpu 取值
      "fpu": "-mfloat-abi=soft",        // 完整 GCC 开关串（无 FPU 也要写 soft）
      "ocd": "target/gd32f1x.cfg",      // 必须是本机 OpenOCD 真实存在的脚本；没有就 null + _note
      "aliases": ["GD32F103XX"],        // 可选：同一条目的其它型号写法
      "flashBase": "0x08000000",        // 可选：系列级覆盖表级
      "ramBase": "0x20000000",          // 可选：生成兜底 .ld 时用
      "_source": "https://…",           // 依据（URL）
      "_note": "歧义与边界说明"
    },
    "CH32V003": {                       // 非 ARM：用 arch/abi/toolchain，cpu 留空
      "cpu": "", "arch": "rv32ec", "abi": "ilp32e",
      "toolchain": "riscv-none-elf-", "fpu": "", "ocd": null
    }
  },
  "flashBase": "0x08000000",            // 表级默认
  "ramBase": "0x20000000",
  "devicePattern": "^([A-Z]{2,6}\\d{2,4}[A-Z]+\\d+)([A-Z])([A-Z0-9])",  // 第 3 捕获组 = 容量码
  "memory": {
    "GD32F103": {"8": {"flash": 65536, "ram": 20480}},                  // 按容量码（需 devicePattern）
    "AT32F403A": {"models": {"AT32F403AVGT7": {"flash": 1048576, "ram": 229376}}}  // 精确型号
  },
  "_memory_comment": ["每个数字的出处 URL"],
  "probes": [{"name": "stlink", "cfg": "interface/stlink.cfg"}]
}
```

### 4.3 数据规则（写错会害人，务必遵守）

1. **不许猜。** 查不到就不写那个键：缺 `memory` 只会"跳过越界校验"，
   而**错的 `memory` 会放过超出真机的链接脚本**。
2. `memory` 两种形式：
   * 按容量码 —— **必须**显式声明 `devicePattern`（表级或系列级），第 3 捕获组 = 容量码。
     形状写错会取到引脚码/型号位 → 变成"按错误容量校验"，所以**没有声明就不查**；
   * 精确型号 `models` —— 命名不规则的厂商（AT32/RP2040/nRF/SAMD/CH32V）走这条；
     一旦写了 `models`，该系列就只认精确表，不再按容量码猜。
3. `ocd` 必须是**本机** `scripts/target/` 下真实存在的脚本名；本机没有就写 `null` 并说明
   （写别的厂商的 cfg 会烧错芯片）。`test_devices_breadth.py` 会逐个核对。
4. 非 ARM 器件：`cpu` 留空 + `arch`/`abi`/`toolchain`；`fpu` 必须为 `""`。
   只写 `cpu: "riscv"` 而不给 `arch` 会被 `_cpu_guard` 确定性拒绝（这是刻意的过渡状态）。
5. 每条数据都要有 `_source`（URL）或 `_note`（依据/歧义）。

## 5. 加一个新后端

后端要提供 4 个动作 + 1 个识别函数，然后 `register(Backend(...))`。

```python
# src/xtcli/backends/<名字>.py
def detect_score(root: Path) -> int: ...            # 0 = 不认；越大越优先
def build_model(root: Path, opt: dict) -> ProjectModel: ...
def action_init(ctx: Context) -> Result: ...
def action_build(ctx: Context) -> Result: ...
def action_burn(ctx: Context) -> Result: ...
def action_doctor(ctx: Context) -> Result: ...

register(Backend(
    name="mybackend",
    aliases=("myalias", "chip123"),                 # -Target 的取值
    detect=detect_score,
    extract=build_model,
    init=action_init, build=action_build, burn=action_burn, doctor=action_doctor,
))
```

要求：

* 动作**返回 `Result(code=...)`**，不要 `sys.exit`；退出码用 `errors.Exit`；
* 任何"不确定"都要先 `model.refusals.append(Refusal(...))`，动作开头用
  `_refusal_result(model)` 兜住；
* 写盘一律走 `managed.Owned`（见第 8 节）；
* `build_model` 收字符串路径也要能跑（`root = Path(root)`）；
* 新后端会**自动**获得 `-Target` 别名、`xtcli-*-pj` 自动分发、统一退出码与日志；
* 记得在 `backends/__init__.py`（或加载清单）里被导入 —— 检查 `load_backends()` 的实现；
* 加一个 `tests/test_<名字>.py`：至少覆盖"认对目录 / 拒绝不写盘 / 参数正确"。

## 6. 加一个新架构 / 新工具链

1. **装工具链到 `E:\env`**（对齐既有约定：版本目录 + junction 稳定别名 + 记录文件），
   见第 11 节；
2. 设备表里给器件写 `arch`（`-march` 值）、`abi`（`-mabi` 值）、`toolchain`（前缀）、
   `cpu: ""`；
3. 运行时链路自动生效，无需改代码：
   * `devices.DeviceInfo` → `ProjectModel.arch/abi/toolchain`；
   * `config_mk.render()` 生成 `ARCH := -march=… -mabi=…` 与 `XT_TOOLCHAIN_PREFIX := …`
     （ARM 工程这两行不出现/为空，保证黄金体积不变）；
   * `cli.py` 发现 `model.toolchain != tools.prefix` 时按新前缀重查工具链，
     找不到 → 环境缺失(3)，**不会退回 ARM**；
   * `rules.mk` 用 `PREFIX := $(XT_TOOLCHAIN_BIN)/$(XT_TOOLCHAIN_PREFIX)`，
     `CFLAGS/ASFLAGS/LDFLAGS` 都带 `$(ARCH)`。
4. `discovery._gcc_candidates(roots, prefix)` 的通用扫描（`<root>/<x>/<y>/bin/`、
   `<root>/<x>/bin/`、`<root>/bin/`）能覆盖常见解压布局；`-` 前缀别名表只对 ARM 生效；
5. 自检：真编一个最小固件并用 `readelf/objdump` 确认架构（`test_riscv.py` 是范例）。

**注意**：兜底 `.ld` 生成目前**只做 ARM**（`linker.py` 顶部有说明）；RISC-V 的启动文件与
`.ld` 必须来自厂商工程。若要让 RISC-V 也有兜底脚本，改 `linker.py` + `gcc_chip._can_generate_ld`
并加测试。

## 7. 改接口的规矩

命令面是**冻结**的，被 `tests/test_architecture.py` 三处断言守着：

* 动词集合 == `FROZEN_VERBS`；
* 选项集合 == `FROZEN_OPTIONS`（4 动词 + 24 选项 / 48 个选项串）；
* `cli.show_help` 的文本里必须列出每个真实选项（文档与实现不许漂移）。

所以新增/删除选项要**同时**改：`cli.build_parser()` → `cli.show_help()` →
`tests/test_architecture.py::FROZEN_OPTIONS` → [使用手册](使用手册.md#42-选项)的选项表 →
README 的速查行。`docs/使用手册.md` 的选项表由
`tests/test_docs.py` 与实现交叉校验（表里的 `-X` 必须与解析器完全一致）。

**不要为了省事加动词**：优先用现有动词 + 选项表达（历史上 `-Clean`/`-MakeTarget`
就是靠选项而不是新命令实现的）。

## 8. 受管写入契约

```python
owned = managed.Owned(model.root)      # 读入 xtcli/.owned.json
owned.write_text(path, text)           # 需要时先备份，再原子写，然后登记
owned.copy_file(src, dst)              # 同上（模板复制）
owned.own_existing(path)               # 只"认领"内容未变的既有文件，不写
owned.flush()                          # 落盘清单
owned.backups                          # 本次产生的备份路径（用于日志）
```

规则（`tests/test_managed.py` 11 项）：

* 目标**不是**清单里的、或清单里有但 SHA256 变了 → 备份成 `<名>.xtcli-bak` 再写；
* 目标是清单里的且未改动 → 直接重写（不产生新备份）；
* 已有同名备份 → **不覆盖**（保留最早那份）；
* 内容与将要写入的完全一致 → 不写也不备份；
* `own_existing` 只用于"上次生成过、这次沿用"的文件，**不能**用来认领用户改过的文件。

新增写盘点时，请一并考虑：是否需要 `own_existing`、是否要在日志里说明备份数量、
是否有对应的 `tests/test_managed.py` 或后端测试。

## 9. 测试体系

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -t tests    # 全部（约 53 秒 / 285 项）
.\.venv\Scripts\python.exe -m ruff check src tests
.\.venv\Scripts\python.exe -m compileall -q src
```

> **新克隆的仓库必须先 `xtcli-setup` 再跑测试。** 工具有一条保护：只认"本仓库自己的
> `.venv`"（防止 conda 底座或错解释器），所以在没引导过的克隆里用别的解释器跑测试，
> 会看到大量以 `未使用项目 venv 运行` 为原因的失败（退出码 3）—— 这是**保护生效**，
> 不是代码坏了。实测：克隆 → `setup.ps1` → 285 项全绿（skipped 里只有硬件/IDF/pyOCD 门控）。

| 类别 | 文件 | 作用 |
| --- | --- | --- |
| 体积黄金值 | `test_build.py` | 三个真实工程 `text/data/bss` 逐字节一致 |
| 架构闸门 | `test_architecture.py` | 零依赖（AST 扫描）、分层、模块 ≤700 行、单一入口、命令面冻结 |
| 文档一致性 | `test_docs.py` | 文档选项表与解析器一致、文档链接存在 |
| 数据↔环境 | `test_devices_breadth.py` | 表里写的 cfg 必须在本机存在；别名/容量/未知厂商行为 |
| 兜底链接脚本 | `test_linker.py` | 生成物与设备表容量一致；GD32 端到端真编 |
| RISC-V 通路 | `test_riscv.py` | CH32V003 端到端，产物必须是 `elf32-littleriscv`，不得出现 `-mthumb` |
| 受管写入 | `test_managed.py` | 备份/清单/不覆盖既有备份 |
| 抽取与拒绝 | `test_extract.py`、`test_generalize.py`、`test_eclipse_family.py`、`test_iar.py`、`test_ioc.py` | 工程解析、拒绝时零写入 |
| 后端 | `test_espidf.py`、`test_sources.py`、`test_flash.py`、`test_memmap.py` | 后端行为与共用工具 |

**黄金体积变化了怎么办**：先判断"是不是构建参数变了"。
参数没变而体积变了 → 说明源码收集/编译规则变了，属于回归，要查清再改；
参数**有意**变了（例如新增默认宏）→ 必须同时更新 `tests/support.py::GOLDEN_SIZE`
并在提交说明里写清楚"为什么这个变化是预期的"。

**新增 fixture**：优先用 `tests/support.py` 的 `make_min_project` / `make_fixture` /
`copy_project`；需要真编的用例请标 `toolchain_ready()` 跳过条件。

## 11. 环境维护（E:\env）

**约定**（`E:\env\README.md` 是权威清单）：

* 带版本号的目录保留版本，升级时新建版本目录，**不原地覆盖**；
* 稳定别名用 **junction** 指向当前版本，工具按别名找到它；
* 不进 PATH（由 xtcli 按前缀发现），需要时用 `XTCLI_ROOTS` 追加搜索根；
* 升级/重装后**更新 `E:\env\README.md`**。

| 组件 | 稳定别名 | 前缀 | 版本 |
| --- | --- | --- | --- |
| ARM Cortex-M | `E:\env\Arm\cortex-m` | `arm-none-eabi-` | Arm GNU Toolchain 15.2.1 |
| RISC-V | `E:\env\RiscV\riscv-none-elf` | `riscv-none-elf-` | xPack GCC 15.2.0-1 |
| make / openocd | `E:\env\msys64\...` | — | GNU Make 4.4.1 / OpenOCD 0.12.0 |
| ESP-IDF | `E:\env\esp\v6.0.1\esp-idf` | — | 6.0.1（工具在 `C:\Espressif\tools`） |

**升级工具链（以 RISC-V 为例）**

```powershell
# 1) 解压新版本到 E:\env\RiscV\xpack-riscv-none-elf-gcc-<新版本>
# 2) 删旧 junction —— 必须用 rmdir，不要用 Remove-Item -Recurse
cmd /c rmdir "E:\env\RiscV\riscv-none-elf"
# 3) 重建 junction
New-Item -ItemType Junction -Path E:\env\RiscV\riscv-none-elf -Target E:\env\RiscV\xpack-riscv-none-elf-gcc-<新版本>
# 4) 验证 + 记录
& E:\env\RiscV\riscv-none-elf\bin\riscv-none-elf-gcc.exe --version
# 更新 E:\env\RiscV\README-RISC-V-toolchain.txt 与 E:\env\README.md，删除旧版本目录
```

xtcli 侧无需改配置（按前缀搜索，别名一换即生效）。

**venv / 缓存**

| 项 | 处理 |
| --- | --- |
| `.venv` 坏了 | `xtcli-setup -Force`（干净重建） |
| `.venv-pyocd` | `xtcli-setup -Pyocd` 单独装；`-Force` 会一并删除 |
| `xtcli.json` 里版本信息过期 | `xtcli <动词> -Refresh` |
| 探针缓存不对 | 删除 `xtcli.json` 的 `probe` 段，或 `xtcli-doctor -Probe` 重认 |

**下载工具链的实测经验**：GitHub 直连可能只有 ~20 KB/s，可用 GitHub 加速前缀
（如 `https://gh-proxy.com/https://github.com/...`）到 ~17 MB/s；**无论走哪个镜像，
都要用官方发布的 `.sha` 校验 SHA256**。另外：被 kill 的后台任务可能留下
`curl` 子进程继续写同一文件，导致 `Get-FileHash` 报"文件被占用" —— 先杀进程再校验。

## 12. 历史事故与教训

改代码前值得读一遍；这些都是实测踩过的：

| 事故 | 现象 | 现在的防线 |
| --- | --- | --- |
| 注入 newlib 桩弄坏本来能编译的工程 | 用户自己实现 `_sbrk`/`_write` 时重复定义；且已写进源码树不自愈 | 按**符号**判定是否补桩；只补到 `xtcli/stubs/` |
| `.ld` 被静默覆盖 | `.cproject` 声明的 `.ld` 在工程外，工程内同名文件被 5376B→55B，日志还谎称"原先不存在" | 有同名文件就保留并告警；`tests/test_extract.py` 守 |
| A 档 `-Clean` 删用户文件 | 执行用户 Makefile 的 clean 删掉了 `precious.txt`、`userdata/` | 只提示不代跑（`gcc_make.action_build`） |
| 大写 `.S` 启动文件导致构建失败 | 报错极具误导性 | `rules.mk` 与源收集都覆盖 `.S`；`test_sources.py` |
| `.cpp` 被静默丢弃 | 构建"成功"但少了文件 | `collect_cpp_sources` + `CXX_SRCS_EXPLICIT` + 指纹 |
| 命令行的 `GCC_ROOT` 破坏工具链 | `cannot execute 'cc1'` | 变量名 `XT_TOOLCHAIN_BIN`；`exec.child_env` 屏蔽 `GCC_ROOT` |
| 显式 `-Target` 绕过识别 | 在错误目录执行 `make clean` | 显式值也必须通过 detect（否则 5） |
| ESP-IDF 后端绕过受管写入 | 静默覆盖 `xtcli/idf-env.json` | 改走 `managed.Owned` + 回归测试 |
| 设备表声称的 cfg 本机不存在 | 烧录在最后一步失败且被报成"烧录失败(7)" | 数据里写 `_note` + burn 前预检（缺失→3） |
| 容量码取错位 | 把引脚码当容量码做越界校验 | 容量码查表必须在数据里显式声明 `devicePattern` |
| RISC-V 的 `sysmem.c` 桩 | `undefined reference to '_estack'` 指向我们写入的文件 | 按 `.ld` 是否定义 `_estack` 决定补不补 |
| `compile_commands.json` 写死 ARM 旗标 | RISC-V 工程里出现 `-mthumb`，clangd 全红 | 按 `arch/abi` 生成（`test_riscv.py` 守） |
| 回读校验以 `halt` 收尾 | 烧录"成功"后芯片停在暂停态：固件不跑、LED 不闪，要手动复位或拔电才恢复 | 回读序列固定为 `reset halt → mdw → reset run → shutdown`；`test_flash.py` 断言最后两条命令必须是 `reset run`/`shutdown` |
| `espidf` 的 `-Clean`/`-MakeTarget` 被忽略 | 用户以为清理过/换过目标 | 映射成 `fullclean` / `idf.py <target>` |
| 删 junction 用 `Remove-Item -Recurse` | 可能穿透 reparse point 删掉**目标目录** | 一律 `cmd /c rmdir` |
| cp936 控制台乱码 | 输出中文报 `UnicodeEncodeError` | 入口 `-X utf8` + `PYTHONUTF8=1`；脚本用 `PYTHONIOENCODING=utf-8` |

## 13. 已知缺口与路线图

**缺口（诚实清单）**

* 烧录全链路**未经真机**（无 ST-Link / ESP32 / CH32V / GD32 / nRF / SAM 硬件）；
* STM32 之外的厂商只验证到"查表 → 构建"；
* `memory` 覆盖 43/68 个系列（其余刻意不猜）→ 缺数据时越界校验会被跳过；
* RISC-V 没有兜底 `.ld` 与启动文件（必须来自厂商工程）；
* CH32V 除 CH32V003 之外的系列（V103/V203/V307，RV32IMAC/IMAFC）未登记；
* `devices.py` 已 450 行，接近"该拆"的规模（查询/校验/别名混在一起）。

**候选下一步（按性价比）**

1. 补 CH32V103/203/307 与更多国产厂商（N32、APT32 等）数据表 —— 只加 JSON；
2. `linker.py` 支持 RISC-V 兜底 `.ld`（段布局/`__global_pointer$` 与 ARM 不同）；
3. 真机验证一轮烧录（有硬件后）：openocd 与 pyOCD 各一条路径 + 回读校验；
4. `devices.py` 拆分（查询 / 校验 / 别名），保持 ≤700 行闸门；
5. 可选：PlatformIO / 独立 CMake 后端（当前明确不接管）。

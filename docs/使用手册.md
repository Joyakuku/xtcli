## 1. 它做什么、不做什么

**做**：从当前目录向上找到工程根，认出这是什么工程、什么芯片，补齐"能编译"所缺的东西
（链接脚本、启动文件、GCC 运行时桩、构建入口），然后调 make（或 `idf.py`）构建，
再烧录并**独立回读校验**。

**不做**（很重要，能省下很多排查时间）：

* 不替换你现有的构建系统。工程自带 `Makefile` 时，它只调用你的 Makefile（A 档）；
* 不改你的源码。补的东西放在 `<工程>/xtcli/` 下；`compile_commands.json` 例外（在根目录，
  且覆盖前会备份）；
* 不猜。缺芯片参数、缺链接脚本又无法生成、链接脚本超出真机容量 —— 一律拒绝并说明原因。

## 2. 安装与升级

```powershell
xtcli-setup              # 建/修项目 venv（独立 CPython；检测到 conda 底座会拒绝）
xtcli-setup -Pyocd       # 额外创建隔离的 .venv-pyocd（只用 pyOCD 烧录时才需要）
xtcli-setup -Force       # 干净重建（连 .venv-pyocd 一起删，再按参数重装）
```

PATH 上有 12 个入口（`E:\env\xtcli\bin` 的 `.cmd`；MSYS/Git-Bash 用 `bin-msys/` 里
同名的无扩展名 wrapper）：`xtcli`、`xtcli-doctor`、`xtcli-setup`、
`stm32-{init,build,burn}-pj`、`esp32-{init,build,burn}-pj`、`pj-{init,build,burn}`。

第一次使用建议先体检：

```powershell
cd E:\path\to\myproject
xtcli-doctor
```

它只读，不写任何东西。输出分三段：**环境**（工具链/探针）、**工程**（识别到什么、
芯片与参数、源文件统计）、**内存布局**（`.ld` 与 `.icf` 的差异、是否超出真机）。

**换机器 / 迁移**：把 `E:\env` 整体搬过去即可（工具链、msys64、xtcli 都在里面）。
必要时用环境变量追加搜索根：

```powershell
$env:XTCLI_ROOTS = "E:\env\Arm\cortex-m;E:\env\msys64\mingw64\bin"
```

或写进 `E:\env\xtcli\xtcli.json` 的 `roots`（**追加**语义，不会丢掉内置默认根）。

## 3. 一分钟上手

### 3.1 STM32（CubeIDE / CubeMX / IAR / Keil）

```powershell
cd E:\Code_workspace\freertos_workspace\software\demo
stm32-init-pj            # 解析 → 补齐 → 生成 xtcli/{config.mk,rules.mk,Makefile} → 试编译
stm32-build-pj           # 直接构建；-Clean 先清理，-MakeTarget size 取体积
stm32-burn-pj            # 烧录 + 回读校验（探针自动识别，结果会缓存）
```

首次 init 会**试编译一次**，所以"init 成功"约等于"能编出来"。不想试编译加 `-NoBuild`。

### 3.2 ESP32（ESP-IDF）

```powershell
cd E:\Code_workspace\esp_study\0_helloworld
esp32-init-pj            # 解析 IDF 环境并固化到 xtcli/idf-env.json（不生成 Makefile）
esp32-build-pj           # = idf.py build
esp32-burn-pj -Port COM7 # UART 烧录；JTAG 用 -FlashType JTAG
```

ESP-IDF 用 CMake+Ninja，所以 init 不生成 Makefile —— 它只把**这次用到的环境**
（IDF 路径、版本、工具目录、Python、target、串口/flashType）记下来，
后续 build/burn 复用；环境变了会提示"与当前解析不一致"。

### 3.3 不确定芯片 / 多厂商

```powershell
pj-init; pj-build; pj-burn      # 等价 -Target auto：按目录特征自动选后端
```

`auto` 认不出时会以 **5（不支持）** 退出并列出工程识别依据；
用 `-Target` 显式指定时**也必须先通过识别**（避免在错误目录里动手）。

### 3.4 RISC-V（CH32V / GD32VF103）

```powershell
cd <你的CH32V工程>
pj-init; pj-build
```

工具会读设备表拿到 `arch/abi/toolchain`，自动切到 `riscv-none-elf-` 工具链
（装在 `E:\env\RiscV\riscv-none-elf`），生成 `-march=rv32ec -mabi=ilp32e`
（CH32V003）或 `-march=rv32imac -mabi=ilp32`（GD32VF103）。
**找不到 RISC-V 工具链时报 3（环境）**，绝不会退回 ARM 工具链把 ARM 参数塞进去。

## 4. 命令与选项总表

命令面**冻结**：动词与选项集合由 `tests/test_architecture.py` 断言，新增必须是有意的改动。

### 4.1 动词

| 动词 | 作用 |
| --- | --- |
| `init` | 初始化到"可编译"（必要时试编译） |
| `build` | 构建 |
| `burn` | 烧录 + 独立回读校验 |
| `doctor` | 只读体检（环境 + 工程 + 内存布局） |

### 4.2 选项

| 选项 | 适用 | 默认 | 说明 |
| --- | --- | --- | --- |
| `-Target` / `--target` | 全部 | `auto` | `auto` / `stm32` / `espidf` / `stm32f4`…（后端的别名） |
| `-Root` / `--root` | 全部 | 自动向上查找 | 指定工程根（最多向上 6 层） |
| `-Config` / `--config` | init/build | `Debug` | 构建配置名（`.cproject`/`.ewp` 里的配置） |
| `-Clean` / `--clean` | init/build | — | gcc：先 `make clean`；espidf：`idf.py fullclean` |
| `-NoBuild` / `--no-build` | init/burn | — | init 不试编译 / burn 不自动先构建 |
| `-NoStubs` / `--no-stubs` | init | — | 不补齐 GCC 运行时桩 |
| `-MakeTarget` / `--make-target` | build | `build`(espidf) | gcc：传给 make 的目标；espidf：`idf.py` 的子命令 |
| `-Interface` / `--interface` | burn | 自动识别→缓存 | openocd interface 配置，如 `interface/cmsis-dap.cfg` |
| `-OcdTarget` / `--ocd-target` | burn | 设备表 | openocd target 配置；**烧录前会预检本机是否存在** |
| `-ProbeSerial` / `--probe-serial` | burn | — | 多探针时指定序列号 |
| `-Bin` / `--bin` | burn | — | 烧 `.bin`（配合 `-Address`） |
| `-Address` / `--address` | burn | 表里的 flashBase | bin 的烧录基址 |
| `-Elf` / `--elf` | burn | 自动找产物 | 指定要烧的固件 |
| `-Flasher` / `--flasher` | burn | `auto` | `auto` / `openocd` / `pyocd` |
| `-FlashType` / `--flash-type` | burn(ESP32) | 工程配置 | `UART` / `JTAG` |
| `-Port` / `--port` | burn(ESP32) | 工程配置 | 串口，如 `COM7` |
| `-Cpu` / `--cpu` | init/build | 设备表 | 覆盖内核，如 `cortex-m4`（设备表未覆盖的型号） |
| `-Fpu` / `--fpu` | init/build | 设备表 | 覆盖 FPU 旗标，如 `-mfpu=fpv4-sp-d16 -mfloat-abi=hard`（取值以 `-` 开头，也可写 `-Fpu=<值>`） |
| `-Probe` / `--probe` | doctor | — | 逐个试探针（每个 8 秒超时） |
| `-Refresh` / `--refresh` | 全部 | — | 重新探测工具链版本（忽略缓存） |
| `-Quiet` / `--quiet` | 全部 | — | 安静模式 |
| `-LogFile` / `--log-file` | 全部 | — | 把输出同时写入日志文件 |
| `-h` / `--help` | 全部 | — | 帮助 |
| `-v` / `--version` | 全部 | — | 版本 |

> 上表就是**全部**选项：`tests/test_docs.py` 会断言"表里的选项集合 == 解析器里的选项集合"，所以文档与实现不会漂移。

### 4.3 退出码

| 码 | 含义 | 典型场景 |
| --- | --- | --- |
| 0 | 成功 | — |
| 1 | 失败 | 未归类的内部失败 |
| 2 | 用法错误 | 未知参数、选项缺取值 |
| 3 | 环境问题 | 缺工具链 / 探针不可用 / ESP-IDF 找不到 / target 脚本本机不存在 |
| 4 | 工程问题 | 认得工程但缺关键件（无 `.ld`、无启动文件、配置名不存在、未构建） |
| 5 | 不支持 | 没有后端认这个目录（显式 `-Target` 也一样要过识别） |
| 6 | 构建失败 | 编译器/链接器报错（含 clean 失败，避免"假成功"） |
| 7 | 烧录失败 | 写片或回读校验失败 |

## 5. 四个动词分别做什么

### 5.1 `init`

1. 找工程根、认后端、解析配置（`.cproject` / `.ewp` / `.ioc` / Makefile / IDF 特征）；
2. **先做确定性检查**：缺芯片参数、非 ARM 却没有 `arch`、`.ld` 超出真机、缺源文件 —— 有问题就拒绝，
   **且不写任何文件**；
3. 补齐：启动文件（找现成的，不生成）、链接脚本（工程没有时复制模板；ARM 且设备表有容量时
   可生成兜底脚本）、GCC 运行时桩（`xtcli/stubs/`）、构建入口 `<工程>/xtcli/{config.mk,rules.mk,Makefile}`、
   `compile_commands.json`（根目录）；
4. 默认**试编译一次**（`-NoBuild` 可跳过）。

```powershell
stm32-init-pj -Config Release      # 用 .cproject 里的 Release 配置
stm32-init-pj -NoStubs             # 我的工程自己实现了 newlib 桩
stm32-init-pj -Cpu cortex-m4 -Fpu "-mfpu=fpv4-sp-d16 -mfloat-abi=hard"
```

### 5.2 `build`

* 优先用 `xtcli/Makefile`（工具生成，B 档）；没有才用工程自带的 `Makefile`（A 档）；
* **A 档不代跑你的 `clean`**：只打印 `make -C <root> -f Makefile clean` 让你自己决定
  （历史事故：某些工程的 clean 会删掉用户数据）；
* 构建前比对 `config.mk` 指纹：与当前配置不一致会告警（陈旧或被改过），提示重新 init；
* 构建后检查产物：make 说成功但产物缺失/比源文件旧 → 告警，防"假成功"；
* `-MakeTarget size|disasm|…` 透传；指定了自定义目标时不再做产物新鲜度检查。

```powershell
stm32-build-pj -Clean
stm32-build-pj -MakeTarget size
esp32-build-pj -MakeTarget size-components
```

### 5.3 `burn`

1. 选固件：默认 `<out_dir>/<target>.elf`（`-Bin` 则 `.bin`），可用 `-Elf` 指定；
   固件不存在且没加 `-NoBuild` 时**先自动构建**；
2. 选烧录器：
   * `-Flasher openocd|pyocd` 直接指定；
   * `auto`：有 openocd **且**知道该芯片的 target 配置 → openocd；否则装了 pyOCD → pyocd
     （靠 CMSIS-Pack 自动拿 flash 算法，不依赖 target 配置）；
3. openocd 路径会**预检 target 脚本在本机是否存在**（例如设备表里写的是较新版本的
   `stm32c0x.cfg`，而本机 OpenOCD 版本较老）：缺失时按**环境问题(3)**退出并给出
   `-OcdTarget` / pyOCD 两条出路，而不是把它报成"烧录失败"；
4. 写片后**独立回读校验**：直接读芯片内存与固件比对（不走 `program` 路径），
   不一致按 7 退出。

```powershell
stm32-burn-pj                          # 自动识别探针（结果缓存，下次直接用）
stm32-burn-pj -Interface interface/cmsis-dap.cfg -ProbeSerial 066FFF...
stm32-burn-pj -Bin -Address 0x08000000
stm32-burn-pj -Flasher pyocd           # 没有 openocd target 配置时的路线
esp32-burn-pj -Port COM7 -FlashType UART
```

### 5.4 `doctor`

只读。会打印：xtcli 版本、搜索根、gcc/make/openocd/pyOCD 及版本、探针脚本目录、
工程识别到的构建配置、后端来源、芯片与系列、CPU/FPU（或 arch/abi）、宏定义、头文件数量、
源码目录、启动文件、链接脚本、库、源文件统计；IAR 工程会额外比对 `.icf` 与 `.ld` 的内存布局。
加 `-Probe` 会逐个试探针（带超时）并记住能连上的那个。

## 6. 工程形态支持矩阵

| 形态 | 识别标记 | init 行为 | 构建 |
| --- | --- | --- | --- |
| CubeIDE / Eclipse | `.cproject` | 生成 `xtcli/` 入口；按配置解析宏/头文件/精确源文件清单 | `xtcli/Makefile` |
| CubeMX（未生成 `.cproject`） | `*.ioc` + `Core/Src` | 参数由 `.ioc` + 目录约定推导，会提示"建议核对 size" | `xtcli/Makefile` |
| IAR | `*.ewp`（+ `.icf`） | 参数取自 `.ewp`；`.icf` 只用于**比对内存布局**并告警 | `xtcli/Makefile` |
| Keil | `*.uvprojx` | 当作"这是 Keil 工程"的信号，参数由 `.ioc`/目录约定推导 | `xtcli/Makefile` |
| 自带 Makefile（A 档） | `Makefile`（无 xtcli 标记） | **跳过初始化**（复用自己的构建系统）；`-Clean` 只提示不代跑 | 你自己的 Makefile |
| ESP-IDF | `CMakeLists.txt` + `project.cmake`/`idf_build_process` | 只写 `xtcli/idf-env.json`（环境快照） | `idf.py build` |
| PlatformIO | `platformio.ini` | 会明确告知"本工具不使用 PlatformIO" | 仍走 arm-none-eabi 构建（若适用） |

判断顺序：`.cproject` > `.ewp` > 自带 Makefile > `.ioc` 推导。

## 7. 芯片覆盖与型号写法

芯片参数外置在 `E:\env\xtcli\data\devices\*.json`，**8 张表 / 68 个系列键**：

| 表 | 覆盖 |
| --- | --- |
| `stm32.json` | STM32 C0 F0 F1 F2 F3 F4 F7 G0 G4 H5 H7 L0 L1 L4 L5 U5 WB WBA WB0 WL |
| `gd32.json` | GD32 E103 E230 E231 F103 F130 F150 F303 F330 F350 F405 F407 F450 + **GD32VF103（RISC-V）** |
| `at32.json` | AT32 F402 F403A F405 F407 F413 F415 F421 F423 F435 F437 WB415 |
| `apm32.json` | APM32 F003 F072 F103 F105 F107 F405 F407 |
| `rp2040.json` | RP2040、RP2350（XIP `flashBase=0x10000000`） |
| `nordic.json` | nRF52840 52832 52833 52810 52811 5340 9160 |
| `samd.json` | SAMD21 SAMD51 SAML21 SAML22 SAME51 SAME54 SAMC21 |
| `ch32v.json` | CH32V003（RISC-V RV32EC） |

**型号写法**：按"最长前缀"匹配，且大小写不敏感，所以
`STM32F103RCTx`、`nRF52840`、`NRF52840_XXAA`、`RP2350A` 都能认。
订货型号带厂商前缀的（Microchip 的 `ATSAMD21J18A`）通过表里的 `aliases` 兼容。

**没覆盖的芯片**会得到确定性拒绝：

```text
[!]  设备表里没有 'XXX' (系列 未知), CPU/FPU 无法确定
     缺少: data/devices/*.json 里该系列的条目
     建议: 加一条设备数据, 或用 -Cpu cortex-m4 -Fpu "..." 覆盖
```

临时救急用 `-Cpu`/`-Fpu`；长期正确做法是往 `data/devices/` 加数据
（规则见[维护手册](维护手册.md#4-加一颗新芯片--新厂商)）。

## 8. 工具链

按型号选前缀 → 在搜索根下找 `{前缀}gcc.exe`：
ARM 用 `arm-none-eabi-`，RISC-V 按设备表的 `toolchain` 字段（`riscv-none-elf-`）。
找不到就报**环境问题(3)**并列出搜索过哪些根，**不会退回另一种架构的工具链**。

| 链 | 本机位置 | 备注 |
| --- | --- | --- |
| ARM GCC | `E:\env\Arm\cortex-m`（junction，`arm-none-eabi-`） | 主工具链，稳定别名不要删 |
| make | `E:\env\msys64\usr\bin\make.exe` | MSYS2 |
| openocd | `E:\env\msys64\mingw64\bin\openocd.exe` + `share\openocd\scripts` | 0.12.0 |
| pyOCD（可选） | `E:\env\xtcli\.venv-pyocd` | 由 `xtcli-setup -Pyocd` 创建，与核心隔离 |
| RISC-V | `E:\env\RiscV\riscv-none-elf`（junction，`riscv-none-elf-`） | xPack GCC 15.2.0-1，来源与 SHA256 见 `E:\env\RiscV\README-RISC-V-toolchain.txt` |
| ESP-IDF | `E:\env\esp\v6.0.1\esp-idf` + `C:\Espressif\tools` | 由 EIM/VSCode 设置/环境变量解析 |

`-Refresh` 可强制重新探测版本；版本会缓存在 `xtcli.json` 里。

## 9. 工具会写哪些文件 / 如何回退

| 路径 | 说明 |
| --- | --- |
| `<工程>/xtcli/config.mk` | 构建参数（含指纹，用于发现"陈旧/被改过"） |
| `<工程>/xtcli/rules.mk` | 构建规则（工具所有，请勿手改） |
| `<工程>/xtcli/Makefile` | 工具的构建入口 |
| `<工程>/xtcli/stubs/*.c` | 补齐的 GCC 运行时桩（`syscalls.c` / `sysmem.c`） |
| `<工程>/xtcli/.owned.json` | **受管清单**：路径 + SHA256 |
| `<工程>/xtcli/idf-env.json` | ESP-IDF 环境快照 |
| `<工程>/xtcli/<型号>_xtcli_FLASH.ld` | 兜底链接脚本（仅当工程与模板库都没有 `.ld` 且能确证容量） |
| `<工程>/compile_commands.json` | clangd 编译数据库 |
| `<工程>/Makefile` | 仅当原本没有时补的转发壳（带 `xtcli:generated` 标记） |
| `*.xtcli-bak` | 覆盖前对"非本工具产物 / 被改过文件"的备份 |

**回退**：直接删掉 `<工程>/xtcli/`（以及可选的 `compile_commands.json`）即可恢复原状；
被备份过的文件用同名 `*.xtcli-bak` 覆盖回去。工具**不会**改你的源码。

**恢复所有权**：如果某个文件你手改了、又希望工具继续管理它，把它改回工具生成的样子
（或删掉）后重跑 init —— 工具只对"自己生成且未改动"的文件直接覆盖，其余一律先备份。

## 10. 故障排查

| 现象（原文） | 退出码 | 原因与处理 |
| --- | --- | --- |
| `没有 backend 能处理该目录` | 5 | 目录里没有可识别的工程标记；`cd` 到工程根，或确认标记（`.cproject`/`Makefile`/`*.ioc`/`*.ewp`/`.uvprojx`/`CMakeLists.txt`/ESP-IDF 特征） |
| `设备表里没有 'XXX' …, CPU/FPU 无法确定` | 4 | 型号没覆盖：加 `data/devices/*.json` 条目，或 `-Cpu`/`-Fpu` 覆盖；先核对型号拼写 |
| `器件 'GD32VF103…' 的内核是 'riscv' (不是 ARM)` | 4 | 该器件在设备表里还没有 `arch`/`abi`/`toolchain`；补上即走 RISC-V 路径 |

`-LogFile build.log` 留证据；`-Quiet` 只保留关键行。

## 11. 未验证与明确不负责

**已验证**（真实工程/真机路径）：

* STM32 三类工程（CubeIDE、IAR、CubeMX 目录约定）的解析、init、构建；
* 三个参考工程体积**逐字节一致**：`demo` 88076/124/25928、`freertos_hal_template`
  16904/96/6488、`1_LED` 5088/12/1068（text/data/bss）；
* 内存越界拦截（1_LED 的 `.icf` 512K/64K vs 真机 256K/48K → 采用更安全的工程 `.ld`）；
* GD32 无 `.ld` 工程的兜底链接脚本 → **真的编过一次**；
* RISC-V（CH32V003 自造工程）init→build，产物经 `readelf` 确认为 `elf32-littleriscv`；
* ESP-IDF 环境解析（真实 IDF v6.0.1 + VSCode 设置 + EIM）。

**未经真机**（手头没有对应硬件）：

* 所有**烧录**路径只验证到参数构造、错误分类、回读校验逻辑，**没有一次真实写片**；
* STM32 之外的厂商（GD32/AT32/APM32/RP2040/nRF/SAM/CH32V）没有真板子，
  已验证"查表 → 架构参数 → 构建"，未验证烧录与上电运行；
* `ocd` 只保证"本机 OpenOCD 里存在该脚本"，不保证该脚本对这颗芯片行为正确；
  CH32V 的 WCH-LinkE 在本机 OpenOCD 里没有配置，烧录需厂商工具或 `-OcdTarget`。

**明确不负责**：

* 不翻译 IAR `.icf` 成 `.ld`（只比对内存布局并告警）；
* 不扫描 `__no_init`/`__root` 等 IAR 专有语义；不解析 Keil `.uvprojx` 的器件与分组；
* 不做 PlatformIO / 独立 CMake 后端；
* 不保证固件与厂商 IDE 逐字节一致（编译器/运行库不同；保证的是**参数与源集合**一致）；
* 兜底链接脚本只含通用段，不含 CCM/DTCM/备份域等厂商特有内存段，且**只做 ARM**。

## 12. 常见问答

**Q：会不会改我的源码？**
不会。补的东西都在 `<工程>/xtcli/`；唯一的例外是 `compile_commands.json`（根目录，
覆盖前会备份）和"原本没有 Makefile 时补的转发壳"。

**Q：多人协作时这些生成物要不要提交 git？**
`xtcli/` 与 `compile_commands.json` 属于本地产物，建议忽略；`*.xtcli-bak` 也不要提交。
（工具本身不依赖 git。）

**Q：我改了 `config.mk` 会怎样？**
下次 build 会告警"陈旧或被改过"，并提示重跑 init —— 不会静默按你的改动继续。

**Q：为什么 `-Clean` 有时候只是打印一条命令？**
那是 A 档（工程自带 Makefile）：它的 `clean` 是你写的，可能删掉任意文件，工具不替你执行。

**Q：A 档（自带 Makefile）能得到什么？**
工具的检测、参数核对、工具链前置（`PATH` 最前放本次选定的工具链 bin）、
烧录与回读校验；构建仍由你的 Makefile 负责。

**Q：换机器要做什么？**
拷贝 `E:\env`（含工具链/msys64/xtcli），运行一次 `xtcli-setup`，然后 `xtcli-doctor` 确认。
`xtcli.json` 里缓存的版本信息可以留着，`-Refresh` 会刷新。

**Q：怎么确认它没把我的工程弄坏？**
`xtcli-doctor` 看参数；构建后比 `build/<target>.map` 或 `-MakeTarget size` 的体积；
`git status` 看工作区（除 `xtcli/`、`compile_commands.json` 外不应有变化）。
